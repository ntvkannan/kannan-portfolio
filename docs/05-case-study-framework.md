# Case Study Framework

**Document:** `05-case-study-framework.md`\
**Purpose:** Standard framework for creating consistent, credible, and
reusable UX/UI case studies across the portfolio.

------------------------------------------------------------------------

## 1. Purpose

This document defines the standard structure, writing principles,
evidence rules, and presentation guidelines for portfolio case studies.

The framework is designed for:

-   Professional UX/UI projects
-   Enterprise SaaS products
-   Web applications
-   Mobile applications
-   Internal business systems
-   Client projects
-   Product design and redesign projects
-   Selected branding or visual-design projects when a case-study format
    is appropriate

The framework provides a **consistent foundation without forcing every
project to tell the exact same story**.

Each case study should reflect the actual project, available evidence,
and the designer's real contribution.

------------------------------------------------------------------------

# 2. Core Principles

## 2.1 Show thinking, not only screens

A case study should demonstrate:

> **Problem → Thinking → Decision → Design → Outcome**

The purpose is not to create a screenshot gallery.

The case study should help a recruiter, hiring manager, or client
understand:

-   What the product/project was
-   What problem needed to be solved
-   What role I played
-   How I approached the problem
-   What design decisions I made
-   How the final experience works
-   What was delivered
-   What was learned

------------------------------------------------------------------------

## 2.2 Evidence before assumptions

Only include information that is supported by:

-   Project documentation
-   Original project files
-   Client-provided information
-   Product screenshots
-   Design files
-   Existing project notes
-   Verified personal project history
-   Measurable results that are actually available

Do not invent:

-   User research findings
-   User quotes
-   Personas
-   User numbers
-   Business metrics
-   Conversion rates
-   Time savings
-   Satisfaction scores
-   Revenue impact
-   Adoption rates
-   Usability-test results
-   Stakeholder statements
-   Project timelines
-   Team sizes
-   Responsibilities that were not actually performed

If information is unknown, write around the gap or mark it as
unavailable.

------------------------------------------------------------------------

## 2.3 Separate fact, interpretation, and inference

When preparing a case study, distinguish between:

### Verified fact

Information directly supported by project material.

Example:

> The platform includes media, layouts, schedules, displays, users,
> permissions, and reports.

### Design interpretation

A reasonable explanation of a design decision based on the interface or
project material.

Example:

> Grouping related content-management functions helps create a clearer
> operational structure.

### Unsupported assumption

A statement that cannot be confirmed.

Example:

> Users were confused by the previous navigation.

Do not present unsupported assumptions as facts.

# 3. Standard Case Study Structure

The following structure is the recommended default.

Not every section is mandatory for every project.

## Core Sections

1.  Hero
2.  Project Overview
3.  Context / Challenge
4.  My Role
5.  UX Approach
6.  Key Work / Design Challenges
7.  Key Screens / Workflows
8.  Outcome
9.  Reflection / Learnings

## Optional Sections

Use only when relevant and supported by project evidence:

-   Product ecosystem
-   Information architecture
-   User flows
-   Research
-   Personas
-   Journey maps
-   Wireframes
-   Prototyping
-   Usability testing
-   Design system
-   Responsive design
-   Accessibility
-   Technical collaboration
-   Before / After
-   Handoff
-   Implementation
-   Design iterations
-   Alternative concepts

------------------------------------------------------------------------

# 4. Section-by-Section Guidelines

## 4.1 Hero

The hero should immediately establish the project.

### Recommended content

-   Project name
-   Short project description
-   Project category
-   Role
-   Product type
-   Primary focus areas

### Example

**OSEL Signage CMS**

> An enterprise digital signage management experience for creating,
> organizing, scheduling, and controlling content across connected
> displays.

**Role:** UX/UI Design\
**Type:** Enterprise SaaS / Signage Management\
**Focus:** Content · Layouts · Scheduling · Displays · Permissions

### Guidelines

Keep the hero concise.

Do not put the entire project story in the hero.

------------------------------------------------------------------------

# 5. Project Overview

Explain the project in a short, understandable way.

### Suggested structure

``` text
What is the product?
Who is it for?
What was the design scope?
What was my role?
```

### Example structure

> \[Product\] is a \[product type\] designed to help \[target users\]
> manage \[primary task\].
>
> I worked on \[scope\] with a focus on \[key UX/UI responsibilities\].

Avoid unsupported audience descriptions if the source material does not
identify them.

------------------------------------------------------------------------

# 6. Context / Challenge

Describe why the project required design work.

The challenge can come from:

-   Product complexity
-   Multiple workflows
-   Information architecture
-   Legacy experience
-   New product requirements
-   Operational complexity
-   Multiple user roles
-   Large amounts of information
-   Device or platform constraints
-   Brand or communication requirements

### Preferred structure

``` text
Context
↓
Design challenge
↓
Why it mattered
```

### Example

> The platform brought together content management, layouts, scheduling,
> displays, permissions, and reporting. The design challenge was to
> organize these connected activities into a coherent enterprise
> experience.

### Important

Do not claim that users experienced a particular problem unless that
problem is documented.

Use neutral language when evidence is limited.

------------------------------------------------------------------------

# 7. My Role

Clearly communicate personal contribution.

### Recommended fields

**Role**

UX/UI Designer

**Responsibilities**

-   Requirement analysis
-   UX planning
-   Information architecture
-   User flows
-   Wireframing
-   UI design
-   Component design
-   Prototyping
-   Design documentation
-   Developer collaboration
-   Stakeholder collaboration
-   Design support during implementation

Only include responsibilities actually performed.

### Collaboration

When known, identify collaboration with:

-   Product managers
-   Developers
-   Business stakeholders
-   Clients
-   Other designers
-   QA teams

Do not invent team structure.

------------------------------------------------------------------------

# 8. UX Approach

Explain how the project was approached.

A general framework can be:

``` text
Understand
    ↓
Structure
    ↓
Explore
    ↓
Design
    ↓
Validate
    ↓
Deliver
```

However, this sequence must not be presented as the actual project
process unless it is supported by project records.

The case study should instead describe the real process when known.

### Possible activities

-   Requirements analysis
-   Existing-product review
-   Information architecture
-   User-flow definition
-   Wireframing
-   Interaction design
-   Visual design
-   Prototyping
-   Design review
-   Developer handoff
-   Implementation support

Only include activities that actually occurred.

------------------------------------------------------------------------

# 9. Product Ecosystem

Use this section when the product contains multiple interconnected
areas.

This is particularly useful for enterprise products.

### Example

``` text
Content
   ↓
Playlist
   ↓
Layout
   ↓
Schedule
   ↓
Display
   ↓
Monitoring
```

The purpose is to show relationships between product areas rather than
displaying isolated screens.

### Good candidates

-   Enterprise SaaS
-   Admin systems
-   CMS platforms
-   ERP systems
-   Workflow products
-   Multi-role applications

------------------------------------------------------------------------

# 10. Information Architecture

Include when navigation and content organization are important to the
project.

### Possible presentation

``` text
Dashboard

Content
├── Media
├── Media Groups
└── Playlists

Layouts
├── Layouts
└── Templates

Scheduling
└── Schedules

Displays
├── Displays
└── Display Groups

Administration
├── Users
├── Roles
└── Permissions
```

The exact structure must come from the project.

Do not create IA that was not actually part of the design.

------------------------------------------------------------------------

# 11. User Flows

Use flows to explain important tasks.

### Recommended format

``` text
Goal
↓
Entry point
↓
Key actions
↓
Decision / configuration
↓
Confirmation
↓
Outcome
```

### Example

``` text
Select media
↓
Create playlist
↓
Create / select layout
↓
Configure schedule
↓
Assign display
↓
Publish
```

Use only workflows that are supported by the project.

------------------------------------------------------------------------

# 12. Key Design Challenges

This is one of the most important sections.

Choose **2--5 meaningful design challenges** rather than describing
every screen.

### Recommended format

## Challenge

What needed to be solved?

## Design Thinking

What did you consider?

## Design Decision

What approach did you choose?

## Result

What changed in the experience?

### Example

**Challenge**

Managing multiple signage entities can create a complex operational
experience.

**Design Decision**

Organize related functions into clear product areas and use consistent
patterns across management screens.

**Result**

The interface provides a more coherent structure for moving between
content, layouts, schedules, and displays.

Only claim a result that can reasonably be supported by the final design
or project evidence.

------------------------------------------------------------------------

# 13. Key Screens / Workflows

This is the primary visual section.

Do not simply place screenshots one after another.

Group screens according to meaningful workflows.

### Example

## Dashboard

Show:

-   Primary navigation
-   Key information
-   Main actions
-   Operational overview

## Media Management

Show:

-   Media listing
-   Filters
-   Groups
-   Playlists
-   Media details

## Layout Builder

Show:

-   Template selection
-   Canvas
-   Regions
-   Media assignment
-   Preview

## Scheduling

Show:

-   Schedule creation
-   Calendar/date controls
-   Assigned layouts
-   Displays/display groups
-   Status

## Display Management

Show:

-   Display list
-   Display details
-   Configuration
-   Status
-   Assigned schedules

## Permissions

Show:

-   Roles
-   Permissions
-   User access

### Screenshot rule

Every screenshot should have a purpose.

Use a short caption explaining what the screen demonstrates.

------------------------------------------------------------------------

# 14. UI / Visual Design

Use this section to demonstrate visual-design quality.

Possible topics:

-   Typography
-   Color
-   Layout
-   Spacing
-   Components
-   Tables
-   Forms
-   Cards
-   Navigation
-   States
-   Responsive behavior
-   Accessibility
-   Design system

Do not turn this section into a generic design-system explanation unless
the project actually involved one.

------------------------------------------------------------------------

# 15. Design System / Reusable Patterns

Include when relevant.

Show how repeated patterns support consistency.

Examples:

-   Buttons
-   Inputs
-   Tables
-   Filters
-   Tabs
-   Cards
-   Status indicators
-   Modals
-   Navigation
-   Form patterns
-   Empty states
-   Error states

### Recommended story

``` text
Repeated problem
↓
Reusable pattern
↓
Consistent application
↓
Improved design coherence
```

------------------------------------------------------------------------

# 16. Before / After

Use only when a genuine before-and-after comparison exists.

### Good use cases

-   Redesign projects
-   Legacy product improvements
-   Navigation restructuring
-   UI modernization
-   Workflow simplification

Do not create a fictional "before" state.

------------------------------------------------------------------------

# 17. Research

Research should be included only when actual research was conducted and
documented.

Possible evidence:

-   Interviews
-   Surveys
-   Usability testing
-   Analytics
-   Customer feedback
-   Stakeholder interviews
-   Competitive research

### Research presentation

``` text
Research method
↓
Key finding
↓
Design implication
↓
Design decision
```

Never invent findings.

Never fabricate participant counts.

Never create fictional quotes.

------------------------------------------------------------------------

# 18. Usability Testing / Validation

Include only if actual validation occurred.

Possible content:

-   What was tested
-   What was observed
-   What changed
-   Why the change was made

If no usability testing was performed, omit this section.

Do not imply that a design was "validated" simply because it was
reviewed.

------------------------------------------------------------------------

# 19. Technical / Development Collaboration

This section is valuable for projects where design and development were
closely connected.

Possible topics:

-   Design handoff
-   Component specifications
-   Responsive behavior
-   Frontend constraints
-   Reusable components
-   Developer collaboration
-   Implementation review
-   Design QA

This section can help demonstrate the transition:

> **UX Strategy → UI Design → Design System → Frontend Development**

Only describe the level of development involvement that actually
occurred.

------------------------------------------------------------------------

# 20. Outcome

Outcome should be based on evidence.

### Three acceptable outcome types

#### A. Measured outcome

Use when verified data exists.

Example:

> Task completion time decreased from X to Y.

#### B. Delivered outcome

Use when the project was implemented but measurable business results are
unavailable.

Example:

> The design was delivered for implementation across the core
> content-management and scheduling workflows.

#### C. Design outcome

Use when the main evidence is the resulting product experience.

Example:

> The final experience brings content, layouts, schedules, displays,
> permissions, and reporting into a unified management interface.

### Do not invent metrics.

Avoid unsupported statements such as:

-   Increased conversions by 40%
-   Reduced task time by 50%
-   Improved satisfaction by 30%
-   Increased adoption by 25%

unless verified.

------------------------------------------------------------------------

# 21. Reflection / Learnings

Use this section to demonstrate senior-level thinking.

Possible questions:

-   What was the most challenging part?
-   What did the project teach me?
-   What would I explore further?
-   What design principle became important?
-   What would I improve with more time?
-   What did I learn about the users/product/domain?

Keep this concise.

The goal is reflection, not repetition.

------------------------------------------------------------------------

# 22. Case Study Writing Style

The portfolio should communicate as a senior designer.

### Use

-   Clear
-   Direct
-   Professional
-   Specific
-   Evidence-based
-   Human
-   Concise

### Avoid

-   Marketing-heavy language
-   Excessive jargon
-   Long paragraphs
-   Generic UX terminology
-   Unverified claims
-   Self-congratulatory statements
-   Artificial metrics

### Prefer

> I structured the navigation around the product's core management
> areas.

Instead of:

> I revolutionized the information architecture to deliver an
> exceptional next-generation experience.

------------------------------------------------------------------------

# 23. Screenshot Guidelines

Screenshots are evidence.

Before using a screenshot, determine:

1.  What does it demonstrate?
2.  Which workflow does it belong to?
3.  Why is it important?
4.  Does it support the case-study story?

### Screenshot categories

-   Product overview
-   Workflow
-   Interaction
-   Detail
-   System / component
-   Responsive
-   Final UI

### Avoid

-   Repeating nearly identical screens
-   Showing screens without context
-   Filling the page with screenshots
-   Cropping important interface elements
-   Showing confidential information
-   Showing unfinished work without explanation

------------------------------------------------------------------------

# 24. Project Evidence Classification

When preparing a case study, classify information as:

  -----------------------------------------------------------------------
  Classification          Meaning                 Usage
  ----------------------- ----------------------- -----------------------
  Verified                Directly supported by   Can be stated as fact
                          project material        

  Observed                Clearly visible in      Can describe what is
                          designs/screens         shown

  Inferred                Reasonable design       Phrase carefully
                          interpretation          

  Unknown                 Not available           Do not invent

  Unsupported             No evidence             Do not include
  -----------------------------------------------------------------------

This classification should be applied before final content is written.

------------------------------------------------------------------------

# 25. Content Length

Case studies should be detailed enough to demonstrate thinking but not
unnecessarily long.

### Recommended

**Small project**

Approximately 5--7 sections.

**Medium project**

Approximately 7--10 sections.

**Complex enterprise project**

Approximately 9--12 sections.

Do not increase length simply to make a project appear more important.

------------------------------------------------------------------------

# 26. Responsive Case Study Presentation

The case-study page itself should work across:

-   Desktop
-   Tablet
-   Mobile

Large product screenshots should remain readable.

Use:

-   Full-width visual sections when appropriate
-   Cropped detail views for focused UI analysis
-   Side-by-side comparisons only when they remain readable
-   Vertical stacking on smaller screens

------------------------------------------------------------------------

# 27. Accessibility

Case-study presentation should follow the portfolio's accessibility
standards.

Include:

-   Meaningful image alt text
-   Sufficient text contrast
-   Keyboard-accessible interactive elements
-   Logical heading hierarchy
-   Reduced-motion support where applicable

------------------------------------------------------------------------

# 28. SEO / Metadata

Each case-study page should have project-specific metadata.

Recommended:

-   Page title
-   Meta description
-   Open Graph title
-   Open Graph description
-   Social preview image
-   Canonical URL when required

Metadata should describe the actual project.

------------------------------------------------------------------------

# 30. Case Study Creation Workflow

Use this workflow for every new project.

``` text
1. Collect project source material
        ↓
2. Review and extract verified information
        ↓
3. Identify project scope and role
        ↓
4. Identify key problems / challenges
        ↓
5. Identify important workflows
        ↓
6. Select meaningful screenshots
        ↓
7. Document design decisions
        ↓
8. Write project-specific Markdown
        ↓
9. Review evidence and remove unsupported claims
        ↓
10. Create case-study wireframe
        ↓
11. Design the page
        ↓
12. Implement in Next.js
        ↓
13. Review desktop / tablet / mobile
        ↓
14. Final content and accessibility review
        ↓
15. Git commit
```

# 31. Case Study Quality Checklist

Before implementation, confirm:

### Story

-   [ ] Project purpose is clear
-   [ ] Challenge is clear
-   [ ] My role is clear
-   [ ] Design contribution is clear
-   [ ] Key decisions are explained
-   [ ] Outcome is appropriately described

### Evidence

-   [ ] Claims are supported
-   [ ] No fabricated metrics
-   [ ] No fabricated research
-   [ ] No fictional quotes
-   [ ] No invented responsibilities
-   [ ] Inferences are clearly framed

### UX

-   [ ] Important workflows are explained
-   [ ] Information architecture is shown when relevant
-   [ ] Design decisions are connected to problems
-   [ ] Screenshots support the story
-   [ ] Complex areas are simplified visually

### UI

-   [ ] Final screens are high quality
-   [ ] Important states are shown
-   [ ] Components/patterns are explained where useful
-   [ ] Screenshots are readable
-   [ ] Visual hierarchy is consistent

### Website

-   [ ] Responsive
-   [ ] Accessible
-   [ ] SEO metadata included
-   [ ] Images optimized
-   [ ] Navigation works
-   [ ] Back-to-work navigation works

# 32. Standard Case Study Philosophy

The portfolio should communicate:

> **I don't just design screens. I understand problems, structure
> complex information, design usable experiences, create consistent
> interfaces, and collaborate through implementation.**

The case study should therefore balance:

**Business / Product Context**

-   

**UX Thinking**

-   

**Interaction Design**

-   

**UI Craft**

-   

**Implementation Awareness**

The final page should feel like evidence of professional design work
rather than a presentation of visual screens alone.

------------------------------------------------------------------------

# 33. Important Rule for AI-Assisted Case Studies

AI may help with:

-   Organizing information
-   Summarizing source material
-   Drafting content
-   Identifying possible case-study sections
-   Suggesting visual presentation
-   Creating implementation structure

AI must not:

-   Invent project history
-   Invent research
-   Invent users
-   Invent metrics
-   Invent business outcomes
-   Invent responsibilities
-   Invent client statements
-   Present assumptions as facts

When source information is incomplete, ask for clarification or use a
conservative description.

------------------------------------------------------------------------

# 34. Reusability Rule

This framework is the **master standard**.

Individual case studies should adapt the framework to the project.

Do not copy the exact same wording from one case study to another.

The following should remain consistent:

-   Overall storytelling quality
-   Evidence standards
-   Role presentation
-   Visual hierarchy
-   Case-study navigation
-   Screenshot treatment
-   Outcome discipline
-   Writing style

The following may change:

-   Number of sections
-   Workflow diagrams
-   Research sections
-   IA
-   User flows
-   Design-system sections
-   Technical sections
-   Number of screenshots
-   Level of detail

------------------------------------------------------------------------

# 36. Final Principle

A strong case study should allow someone who has never seen the project
to understand:

> **What was the product?**

> **What problem did I work on?**

> **What was my responsibility?**

> **How did I approach it?**

> **What did I design?**

> **Why did I make those decisions?**

> **What was delivered?**

> **What did I learn?**

If the case study answers these questions clearly, it has fulfilled its
purpose.
